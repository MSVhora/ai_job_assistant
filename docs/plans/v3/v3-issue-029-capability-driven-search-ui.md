# Issue #29 — Capability-driven search UI: ui primitives + generic per-source filter form (M3)

**Status:** Done (merged)
**Tracks:** GitHub issue #29 (milestone `v3`, M3 advanced filters — frontend part, delivered with two /jobs placement additions)
**Plan of record:** [v3-implementation-plan.md](v3-implementation-plan.md) §2 D5; §4 M3 (frontend)
**Depends on:** #28 (merged — `/api/sources` returns `filters: list[SourceFilterDecl]`; `SourceQuerySpec.options` exists and is validated/typed in `schema.d.ts`)
**Blocks:** nothing (last issue of v3)

---

## Goal

The search UI renders each source's declared filter set from `/api/sources` —
zero per-source components. New sources get correct, validated filter forms
automatically. Along the way, the hand-rolled `select`/`checkbox`/accordion
markup becomes reusable, a11y-correct `components/ui/` primitives.

The backend is untouched: types are already generated (`SourceFilterDecl`,
`SourceInfoResponse.filters`, `SourceQuerySpec.options` all exist in
`lib/api/schema.d.ts` and are currently unused by the UI).

## Locked decisions

| Decision | Choice | Rationale |
|---|---|---|
| UI primitives, no new deps | `components/ui/select.tsx` (styled native `<select>`), `checkbox.tsx` (styled native checkbox), `accordion.tsx` (controlled disclosure: trigger button + `aria-expanded` + `aria-controls` + chevron, extracted from the current `SearchQueriesCard` pattern) | Radix Select/Checkbox/Accordion considered and rejected: native elements are already keyboard/screen-reader correct, work directly with react-hook-form `register`, and the repo already hand-styles native controls — three duplicated style constants (`selectStyles` in `MatchFilterPanel.tsx:6`, `SELECT_STYLES` in `profile/fields.tsx:382`, inline string in `SearchForm.tsx:200`) collapse into one primitive. New dependency would be churn, not capability |
| Accordion behavior | Single-open (one source expanded at a time), like today; content region gets `role="region"` + `aria-labelledby` tied to the trigger | Preserves existing UX; `role="region"` makes expanded content a navigable landmark (a11y test target) |
| Form values | `QueryFieldValues` gains `options: Record<string, string \| boolean>`; strings for text/number/select/multiselect-text (comma-separated for multiselect), real booleans for boolean | One flat RHF-recordable shape; numbers arrive as strings from `<input type="number">` and are coerced at submit — same pattern as the existing `minSalary` field. Multiselect-text (LinkedIn `company_ids`) stays a comma-separated input, consistent with `skills`/`exclude` — chips would be a new primitive with no second consumer |
| Schema factory | `searchFormSchema` becomes `makeSearchFormSchema(sources: SourceInfo[])`: the per-source query object's `options` sub-schema is built from that source's `filters` declarations — `text` → capped string; `number` → empty-or-integer refine; `select` → declared `option.value` enum (empty string = unset); `boolean` → `z.boolean()`; `multiselect-text` → capped string (split at submit). Key cap 12 mirrors the backend. `SearchForm` builds it via `useMemo` on `sources` | Issue body: "Zod schema generated from the declarations". Sources are fully loaded before `SearchForm` renders (`JobsPageClient` gates on them), so the factory is never built against an empty/partial declaration set. Client-side validation is convenience only — the backend remains source of truth (400 on bad options, per #28) |
| Options rendering | New `SourceFiltersForm` feature component: maps `SourceFilterDecl[]` → fields via a per-`type` switch (`Select` / `Checkbox` / `Input`), each wrapped in the existing `Field` (label, hint from `help_text`, placeholder from `placeholder`, error slot); rendered under an "Advanced filters" subheading inside the per-source accordion body, after title/skills/exclude. No `filters` on a source → no subheading, nothing rendered | Zero per-source components per the issue; `Field` already gives the label/error/hint a11y contract the standards require |
| Registration paths | `queries.${source.name}.options.${decl.key}` via `useFormContext` | RHF dynamic record paths, same as the existing per-source title/skills fields |
| Payload mapping | `toSearchRequest` gains options handling per source: number strings → `Number()` (only when finite), select/text → non-empty strings, multiselect-text → `splitList()`, booleans passed through only when `true` (absent = unset); result rides in `source_queries[name].options` | Backend contract from #28: `dict[str, str \| int \| bool \| list[str]]`, ≤12 keys; `false`/`""` are indistinguishable from unset for the connectors, so they are omitted rather than sent |
| Stored-query seed | The `SearchForm` re-seed effect also seeds `options` from `storedQueries.queries[name].options ?? {}` (v2 specs generated by the #28 LLM flow already carry options) | Without this, regenerated LLM-chosen options (e.g. `sort_by: relevance`) are invisible/uneditable in the form; D6 says AI-generated and user-edited filters are one schema |
| `supports_exclusions` stays | The UI keeps reading `supports_exclusions` for the exclude field, and the backend field is **not** removed in this issue | Deviation from #28's note ("removed in #29 when the UI stops reading it"): `exclude` is a top-level `SourceQuerySpec` field, not a declared option, so the declarations cannot express it — removing the flag would orphan the exclude field. Flagged for owner sign-off; removal would mean either declaring `exclude` as a filter (backend change) or dropping the feature |
| Regenerate a11y | Regenerate status text moves into an `aria-live="polite"` region next to the button (regenerating / done / failed), keeping the existing stale-notice `role="status"` | Issue test list names "aria-live on regenerate"; today only the button label changes, which is not announced |
| `MatchFilterPanel` untouched | Out of scope (issue body); the sidebar `posted_within_days` filter is unrelated to search-run options | v3 plan §4 M3 |
| Tests — new framework | Add `vitest` + `@testing-library/react` + `@testing-library/user-event` + `jsdom` as devDependencies, `npm test` script (`vitest run`, also wired into the do-done gates) | Issue body requires component tests ("form renders fields for both sources from fixture declarations; values reach the API payload; a11y") and the frontend has no test runner at all. Vitest is the Next/Vite-ecosystem default, zero-config TS/ESM; Radix-free components need no browser, jsdom suffices. Justified as the only way to meet the issue's test scope |
| New external deps summary | 4 devDependencies (vitest, jsdom, two testing-library packages). No runtime deps | Everything else is built on native elements + existing stack (react-hook-form, zod, Tailwind) |

### Scope addition (owner, 2026-09-15, decision #2 below)

Two /jobs placement changes folded into this issue:

1. **Profile selector into the filter sidebar** — rendered at the top of the
   `<aside>` (own bordered section), sharing the page's `activeProfileId` state and
   `selectProfile` handler with the Global configuration dialog copy; both always show
   the same track. `ProfileSelector` extracted into `ProfileSelector.tsx` (hint text
   now a prop so each placement says the right thing).
2. **Priority slider into `MatchFilterPanel`** — the slider re-weights stored matches
   at read time exactly like `sort`/`posted_within_days`, so it belongs with them, and
   is **removed from the Global configuration dialog** (owner: a read-time view control
   has no reason to be in a run-definition dialog). No behavior change: still the
   server-side `priority` query param with debounced per-profile persistence.

## Scope

### Primitives (`components/ui/`)

- `select.tsx`: `<select>` with the consolidated select styles (focus-visible
  ring, `aria-invalid` styling matching `input.tsx`), forwards props.
- `checkbox.tsx`: single checkbox with label-aside styling (for boolean
  options); forwards props, keeps the native input in the accessibility tree.
- `accordion.tsx`: `AccordionItem({ id, open, onToggle, trigger, children })`
  encapsulating trigger button (`aria-expanded`, `aria-controls`, rotating
  chevron) + conditional content region. `SearchQueriesCard` refactored onto
  it — markup identical, state stays in the card.

### Feature components (`components/features/jobs/`)

- `SourceFiltersForm.tsx`: generic, declaration-driven field renderer (per
  the Locked decisions). Props: `sourceName: string`, `decls: SourceFilterDecl[]`.
- `search-form-schema.ts`:
  - `QueryFieldValues` + `emptyQueryFields()` gain `options`.
  - `makeSearchFormSchema(sources)` factory per the Locked decisions;
    existing static exports (`POSTED_WITHIN_OPTIONS`, `seedSpec`,
    `splitList`, `supportsExclusions`) unchanged.
  - `toSearchRequest`: builds `options` per source (drop empty/unset), keeps
    the existing title/skills/exclude and `max_days_old` logic.
- `SearchQueriesCard.tsx`:
  - Prop type widened to full `SourceInfo` (or at least adds `filters`) —
    today `SearchForm.tsx:126–130` strips `filters` when mapping props.
  - Accordion body renders `SourceFiltersForm` after the text fields.
  - Regenerate status in `aria-live` region; accordion via `ui/accordion.tsx`.
- `SearchForm.tsx`: schema via `useMemo(makeSearchFormSchema, [sources])`,
  pass full source objects through, seed `options` in the re-seed effect.

### Tests (`frontend/` — new)

- `components/features/jobs/SourceFiltersForm.test.tsx`: renders fields for
  both sources from fixture declarations copied from the backend's actual
  declarations (Adzuna: boolean + number + select; LinkedIn: select + number
  + boolean + multiselect-text + text) — correct control per type, labels,
  `help_text` shown.
- `search-form-schema.test.ts`:
  - `makeSearchFormSchema` rejects an undeclared option key and an
    undeclared select value; accepts valid ones.
  - `toSearchRequest`: options reach `source_queries[name].options` with
    native types (int for number, bool, `string[]` for multiselect-text);
    empty/unset values omitted; existing behavior unchanged (regression for
    title/skills/exclude/max_days_old).
- A11y test: accordion trigger toggles `aria-expanded`; labels associated
  with controls (getByLabelText); regenerate status region marked
  `aria-live`.
- `package.json`: `"test": "vitest run"`; test files excluded from the
  production build if Next tries to compile them.

### Gates

- `npm run lint && npm run build && npm test` green in `frontend/`.
- Live check: both sources' advanced filters fillable in the accordion,
  submitted payload contains correct `options` (verify in network tab or
  backend logs); an option cleared in the UI is absent from the payload.
- Docs: `docs/guide/03-job-discovery-and-matching.md` — filter tables gain a
  "the form is generated from these declarations" note (UI behavior change).
  Diagrams: no architecture change (no new API/DB surface), but re-run
  `node scripts/render-diagrams.mjs` per the issue's definition of done.
- No backend change, no migration, no `generate:api` run (types already
  current from #28); `.env.example` unchanged.

## Risks

| Risk | Mitigation |
|---|---|
| RHF dynamic `options.<key>` paths with a schema rebuilt per sources load | Sources load before the form mounts; schema memoized on `sources` identity; tests cover the factory |
| Number coercion surprises (e.g. `""`, `12.5`) | Strings in form state, integer-only refine + finite check at submit — bad input blocked client-side and by the backend 400 |
| Test framework addition slows CI/build | vitest run only in the explicit gate; `next build` untouched (test files outside `app/`, excluded if needed) |

## Out of scope (this issue)

- Backend anything (declarations, validation, mapping — #28, merged).
- `MatchFilterPanel` changes; match/read-side filters.
- Removing `supports_exclusions` from the backend or the UI (⚠ flagged in
  Locked decisions — needs owner sign-off).
- Chips/tag-input UI for multiselect-text; per-source min/max bounds on
  number options (same deferral as #28).
- New sources or new filter types beyond the declared five.
